# rules — このツリーの書き方

**このファイルに索引はない。** 索引は `docs/bin/doc`(引数なし)が各 topic README
の先頭2行から生成する。読むときは `doc`、書くときはこのファイル。

```sh
docs/bin/doc                      # 索引(探し方 + 全 topic の一覧)。まずこれ
docs/bin/doc show <topic>#<節ID>  # その節だけ
docs/bin/doc grep <パターン>      # 見出し単位でヒット位置と行範囲
docs/bin/doc log [<パターン>]     # CHANGELOG のエントリ一覧
docs/bin/doc check                # このファイルの規約に違反していないか
```

`docs/bin/doc` は devsandbox ホストの `/usr/local/share/doc/bin/doc` からフォーク
した同じパーサー(index/show/grep/log/toc/check)。詳しくはそのファイル冒頭の
docstring を参照。

## 変更を記録するルール {#record}

**どこに書くかは1つに決まる。同じ内容を2箇所に書かない。片方はリンクにする。**

| 書くもの | 行き先 |
|---|---|
| 日付が付くもの(いつ・何を変えたか、その日の動作確認) | `CHANGELOG.md` |
| 現在形で書けるもの(今こうなっている) | `<topic>/README.md` |
| なぜそうしたか・何を採らなかったか | `<topic>/README.md` の `## 設計判断の記録` |

**動作確認は CHANGELOG に書く。** 日付付きの証拠であって、現在形の文書では腐るため。
例外は「恒久的な性質」を発見した検証(例: このコンテナに procps が無い)で、それは
事実なので topic README に残す。

CHANGELOG の各エントリ(`## YYYY-MM-DD — ...`)には明示的に `{#id}` を付ける
(`doc check` が強制する)。

## 新しいトピックを足すとき {#newtool}

`<topic>/README.md` を作り、下の形で埋めて `docs/bin/doc check` を通すだけ。
**索引は触らない**(生成される)。

```markdown
# <topic> — <一行の説明>

**いつ読むか**: <発火条件を / 区切りで>

## 構成              構成図、データの流れ、ファイル間の依存関係
## 構成ファイル一覧   表: ファイル → 役割
## 運用              起動・確認・ログ・はまりどころ
## 既知の制限
## 設計判断の記録     採らなかった案とその理由。常に最後
```

- 節名は固定文字列(`doc` が `usage arch files security ops limits design` に
  写像する)。省略は可、並べ替えは不可。独自の節名を作る場合は見出し末尾に
  `{#id}` を付ける。
- **`## 設計判断の記録` 以外は現在形で書く。** 他の節に日付の追記が現れたら
  それはバグ(CHANGELOG に移す)。
- **`いつ読むか` は発火条件で書く。** トピックの言い換えではなく、読み手の状況
  (「クライアントとサーバーのROOM_PROP周りを触る」)。

## 書き方の固定ルール {#style}

- **相互参照は行番号でなく `topic#節ID`。** 行番号は編集でずれる。標準節は
  `dev-environment#ops` のように暗黙のIDで指せる。
- このリポジトリの外(devsandboxホストのインフラ機構そのもの)を説明しない。
  「ここではこう使う・こう困る」という事実だけを書き、仕組みの説明はホスト側の
  ドキュメント(`doc show <topic>`、このリポジトリの読者には見えないので固有名詞
  だけ添える程度に留める)に委ねる。

## 削除したものを取り戻す {#recover}

このツリーは通常の git 管理下にある。削除した内容は `git log -p -- docs/<path>`
で追える。
